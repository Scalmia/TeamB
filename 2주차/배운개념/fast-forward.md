## 기본설명

git의 브랜치는 사실 "커밋들이 한 줄로 이어진 목록 + 그중 맨 끝을 가리키는 이름표(포인터)"일 뿐이다. `main`이라는 브랜치는 실제로는 특정 커밋을 가리키는 포인터에 불과하다.

**fast-forward(빨리감기) 병합**은, 내가 합치려는 다른 브랜치(예: `origin/main`)가 내 브랜치의 커밋들을 **그대로 이어서 앞서나간 상태**일 때만 일어난다. 이 경우 git은 "합친다"는 실질적인 작업을 할 필요가 없다 — 그냥 내 `main` 포인터를 상대방이 가리키는 커밋으로 옮기기만(포인터 재할당) 하면 끝난다. 충돌이 안 나는 이유는 git이 뭔가 똑똑하게 자동으로 풀어주는 게 아니라, **애초에 합칠 내용이 없기 때문**이다. 내 히스토리가 상대방 히스토리의 부분집합이라, 포인터만 앞으로 밀면 상대방 커밋까지 자동으로 내 것이 된다.

반대로 내 브랜치와 상대 브랜치가 **각자 다른 커밋을 따로 쌓아서 갈라진 상태(divergence)**라면 fast-forward가 불가능하다. 이때 git은 진짜로 "병합 커밋"을 새로 만들어서 두 갈래를 하나로 합쳐야 하고, 같은 파일의 같은 부분을 양쪽이 다르게 고쳤다면 그게 바로 **충돌(conflict)**이다.

즉 "왜 충돌 없이 자동으로 흡수되는가"에 대한 답은: **내가 아직 로컬에 커밋을 하나도 안 쌓은 시점에 미리 원격 최신 커밋들을 받아오기 때문**이다. 이 타이밍에 pull하면 내 브랜치엔 새로 갈라진 게 없으니 무조건 fast-forward가 되고, 그 다음에 내 커밋 하나를 그 위에 얹어서 push하면 그것도 다시 fast-forward가 된다.

## 우리 프로젝트에서의 활용처

**TeamB 저장소 자체가 이 원리를 실제로 증명하고 있다.** `git log --merges`로 확인한 결과 TeamB의 커밋 18개 전부가 병합 커밋 없이 일직선으로 이어져 있다 — 즉 지금까지 이 저장소에 있었던 모든 반영은 예외 없이 fast-forward였다.

이게 우연이 아니라 **강제된 규칙**이라는 근거는 이 스킬 자신에게 있다:
- `~/.claude/skills/meeting-minutes/SKILL.md`, `~/.claude/skills/study-note/SKILL.md` 둘 다 git 안전장치 3단계에서 `git pull --ff-only`를 씀. `--ff-only`는 "fast-forward가 가능할 때만 pull을 허용하고, 아니면 그냥 실패시켜라"는 명시적 옵션이다.
- 두 스킬 모두 이 명령이 실패하면(즉 진짜 병합이 필요한 상황이 오면) **자동으로 병합을 시도하지 않고 무조건 중단**하도록 되어 있다. "충돌 가능성이 있는 상황 자체를 자동화 대상에서 제외"하는 설계다.
- 그래서 이 저장소는 매번 커밋 직전에 pull하고(그 시점엔 항상 fast-forward), 파일 하나만 커밋해서 push하는(그것도 fast-forward) 패턴만 반복해왔다.

**반대 사례(진짜 병합 커밋)도 Zeteo 저장소에 남아있다.** `origin/main`의 커밋 `e887783`("merge: 유민성님 백엔드 구조 채택 + 파트 C 화면 · 파트 B 봇 통합")은 실제 병합 커밋이다. `git log --graph`로 보면 이 지점에서 그래프가 갈라졌다가 다시 합쳐지는 다이아몬드 모양이 나온다 — 유민성님이 독립적으로 쌓아온 커밋들(`f7be7aa`, `934b42d` 등)과 팀 저장소 쪽 커밋(`9c20437`)이 서로의 연장선이 아니라 각자 갈라져 있었기 때문에 fast-forward가 불가능했고, git이 두 히스토리를 억지로 합치는 병합 커밋을 만들어야 했다. (이때 실제로 세미콜론·prettier 설정 차이 때문에 파일 여러 개가 통째로 충돌했던 것도 팀 기록에 남아있다.)

## 퀴즈

1. fast-forward 병합이 일어날 때 git이 실제로 하는 일은?
   - 정답: 브랜치 포인터를 상대 브랜치의 최신 커밋으로 옮기기만 함 (해설: 새로 합칠 내용을 계산하는 게 아니라, 내 히스토리가 상대 히스토리의 부분집합이라 포인터만 밀면 끝남.)

2. `git pull --ff-only`가 실패한다는 건 무슨 뜻일까?
   - 정답: 로컬과 원격 히스토리가 서로 갈라져서(divergence) 단순 포인터 이동으로는 합칠 수 없다는 뜻 (해설: 이 경우 진짜 병합 커밋이 필요하고, 같은 부분을 다르게 고쳤다면 충돌이 날 수 있다. TeamB의 스킬들은 이 상황을 자동 해결하지 않고 무조건 중단하도록 설계돼 있다.)

3. TeamB 저장소가 18개 커밋 내내 한 번도 병합 커밋 없이 일직선인 이유는?
   - 정답: 커밋 직전에 항상 `git pull --ff-only`로 최신 상태를 먼저 받아온 뒤, 새 파일 하나만 커밋해서 바로 push하는 패턴을 반복해서 — 매 순간 로컬이 원격보다 앞서나가는 갈라짐이 생길 틈이 없었기 때문 (해설: 여러 사람이 각자 다른 파일을 만들어도, "커밋 전 pull"이 지켜지는 한 히스토리는 계속 일직선을 유지한다.)

4. Zeteo의 `e887783` 커밋이 fast-forward가 아니라 진짜 병합 커밋이었던 이유는?
   - 정답: 유민성님 저장소와 팀 저장소가 각자 독립적으로 커밋을 쌓아서 두 히스토리가 서로의 연장선이 아니라 갈라진 상태였기 때문 (해설: 한쪽이 다른 쪽의 부분집합이 아니면 fast-forward 자체가 불가능하고, git은 두 갈래를 합치는 병합 커밋을 새로 만들어야 한다.)
