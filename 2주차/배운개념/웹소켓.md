## 기본설명

일반적인 HTTP 통신은 "클라이언트가 물어봐야 서버가 답하는" 구조라, 서버 쪽에서 먼저 클라이언트에게 뭔가를 알려줄 방법이 없다. 웹소켓(WebSocket)은 클라이언트-서버 사이에 한 번 연결을 맺으면 그 연결을 계속 열어두는 방식이라, 서버든 클라이언트든 원하는 시점에 아무 때나 먼저 메시지를 보낼 수 있다(양방향·지속 연결). 이 덕분에 "다른 사람이 방금 한 행동을 나머지 전원 화면에 실시간으로 반영"하는 것 같은 기능을 매초 서버에 다시 물어보는(폴링) 방식보다 훨씬 빠르고 가볍게 구현할 수 있다.

Zeteo 프로젝트는 웹소켓 표준 API를 직접 쓰지 않고 **Socket.IO** 라는 라이브러리를 쓴다. Socket.IO는 웹소켓을 기반으로 하되, 연결이 끊기면 자동 재연결, 웹소켓을 못 쓰는 환경에서는 다른 방식으로 자동 대체(fallback), 그리고 "room"이라는 그룹 단위로 메시지를 묶어 보내는 기능까지 얹어놓은 상위 도구다. 그래서 정확히는 "웹소켓을 쓴다"보다 "웹소켓 기반의 Socket.IO를 쓴다"가 더 정확한 표현이다.

## 우리 프로젝트에서의 활용처

Zeteo는 "라이어 게임 속에 숨은 봇 1명을 찾는" 5인 소셜 디덕션 게임이라, 한 사람의 행동(투표·채팅·페이즈 전환)이 나머지 전원 화면에 지연 없이 반영돼야 한다. README의 설계 원칙 1~3번이 이 이유를 그대로 설명하고 있다: **서버가 단일 진실 공급원**(클라이언트는 그리기만 함) · **상태는 항상 통째로 전송**(증분 전송 없음, 이벤트를 놓쳐도 다음 상태로 자동 복구) · **타이머의 진실도 서버**(`deadlineAt` 절대시각만 보내고 클라이언트가 매 틱 재계산). 이 세 원칙 모두 "지속적으로 열려 있는 연결"이 전제라 웹소켓(Socket.IO)이 필요했다.

실제 코드 위치 (조사 시점 가장 최신인 `origin/dev` 기준, `origin/main`엔 더 단순한 초기 버전이 있음):

- `apps/backend/src/index.ts` — 서버 쪽. `import { Server } from 'socket.io'`로 소켓 서버를 열고, `io.on('connection', (socket) => ...)`에서 클라이언트 접속을 받는다. 클라이언트가 `socket.emit('action', ...)`으로 보낸 행동을 `socket.on('action', ...)`에서 받아 처리한 뒤, `socket.join(action.roomId)`로 그 소켓을 게임방(room) 단위로 묶고, `io.to(socketId).emit('event', event)`로 같은 방에 있는 플레이어들에게 갱신된 상태를 되쏜다.
- `apps/frontend/src/net/socket.ts` — 클라이언트 쪽. `socket.io-client`로 소켓 인스턴스를 만들고(`io({ autoConnect: false })`), `sendAction()`으로 서버에 행동을 보내고 `onServerEvent()`로 서버가 보낸 상태 갱신을 구독한다. 프론트는 이 파일 하나만 통해서 서버와 통신하고, 나머지 화면 컴포넌트는 이 함수들만 갖다 쓴다.
- `apps/frontend/vite.config.ts` — 개발 환경에서 `/socket.io` 경로를 백엔드(`localhost:3000`)로 프록시(`ws: true`)해서, 프론트 개발 서버와 게임 서버가 다른 포트여도 웹소켓 연결이 그대로 통하게 해준다.

참고로 `origin/main`에는 `'state'`라는 이벤트 이름을 쓰는 더 단순한 초기 버전이 있고, `origin/dev`·`origin/feat/*` 브랜치들은 이벤트 이름이 `'event'`로 바뀌고 로직도 훨씬 커진(80줄 → 350~550줄) 버전이라, 팀이 작업하면서 프로토콜을 한 번 확장한 것으로 보인다.

## 퀴즈

1. 일반 HTTP 요청-응답 방식 대신 웹소켓을 쓰는 가장 근본적인 이유는?
   - 정답: 서버가 클라이언트의 요청 없이도 먼저 메시지를 보낼 수 있어서 (해설: HTTP는 클라이언트가 요청해야만 서버가 응답하는 구조라, "다른 플레이어의 행동을 즉시 반영"하려면 서버가 주도적으로 push할 수 있는 지속 연결이 필요하다.)

2. Zeteo가 실제로 사용하는 것은 순수 웹소켓 API일까, Socket.IO일까?
   - 정답: Socket.IO (해설: `apps/backend/package.json`에 `socket.io` 의존성이 있고, `index.ts`에서 `import { Server } from 'socket.io'`로 서버를 연다. Socket.IO는 웹소켓 위에 자동 재연결·fallback·room 기능을 더한 라이브러리다.)

3. Zeteo 서버가 상태를 클라이언트에 보낼 때, 바뀐 부분만 보낼까 전체를 다 보낼까?
   - 정답: 항상 전체 상태를 통째로 보낸다 (해설: README 설계 원칙 2번 — 증분 전송을 하지 않아서, 중간에 이벤트를 하나 놓쳐도 다음 상태를 받으면 자동으로 복구된다.)

4. 백엔드 코드에서 `socket.join(action.roomId)`와 `io.to(socketId).emit(...)`은 각각 무슨 역할을 할까?
   - 정답: `join`은 해당 소켓을 특정 게임방(room)에 묶는 것, `io.to(...).emit`은 그 방(또는 특정 소켓)에게만 메시지를 보내는 것 (해설: Socket.IO의 room 기능 덕분에 서버가 "이 방에 있는 사람들에게만" 상태를 broadcast할 수 있다 — 다른 방 게임 상태가 섞이지 않는다.)
